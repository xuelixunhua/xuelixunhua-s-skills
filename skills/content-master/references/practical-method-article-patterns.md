# 方法论文章的避坑清单写法

这个参考用于工具分享、数据处理、业务方法论、流程复盘类文章。它只在读者已经知道目标、但容易卡在隐藏门槛时使用，不作为固定模板。

## 适用信号

- 读者以为拿到工具或数据就能开始，但中间有文件格式、单位口径、权限、入口、映射关系等隐藏坑。
- 文章有很多专业细节，如果按顺序平铺，读者会先迷路再失去耐心。
- 作者真正想传递的是一套判断口径，教程只是载体。
- 有可以复用的代码、仓库、表格或工具，但正文不适合写成命令行手册。

## 核心结构

推荐顺序：

1. 先还原一个具体卡点，让读者意识到问题真实存在。
2. 给一张全局避坑清单，把隐形流程变成可扫描地图。
3. 按清单逐关拆解，每一关都讲清“原始状态 -> 错用后果 -> 正确处理 -> 为什么”。
4. 工具或 GitHub 入口尽早交代，但正文重点放在业务口径和判断逻辑。
5. 结尾承接下一步：这一篇解决什么，下一篇才进入什么。

## 避坑清单表的写法

清单表的作用是给读者一张阅读地图。常用列：

| 列名 | 作用 |
|---|---|
| 关口 | 把复杂流程拆成可命名的关卡 |
| 原始状态 | 告诉读者真实拿到的东西是什么 |
| 如果直接用 | 制造避坑价值，说明错误后果 |
| 正确处理 | 给出可执行动作或判断口径 |

写表时避免把长段落塞进去。每一格只放一个短判断，后文再展开最关键的几行。

## 加粗和金句

加粗用于提醒，不用于表演。

优先加粗这些句子：

- 读者必须记住的业务口径。
- 有一点幽默感、但同时非常准确的提醒。
- 文章主线的转折句或阶段性结论。

不要为了制造金句强行加粗抽象话。好句子通常来自真实痛点，比如“只看一个方向会漏风”，少写凭空制造的宏大判断。

## 工具与代码的摆放

如果正文面向业务读者，代码优先用来解释口径，少展示技术能力。

- GitHub、demo、工具链接可以在开头或靠近相关段落轻量说明。
- 不要单独设一个只服务作者意图的标题，例如“代码放在 GitHub，正文只讲口径”。标题应该回答读者此刻关心的问题。
- 如果仓库没有附带某个数据、密钥、掩膜、商业接口或内部文件，必须明确边界，不要写成读者可以直接取用。

## 质量检查

交付前快速问：

- 开头有没有具体到一个真实卡点？
- 清单表是否让读者一眼看懂全局风险？
- 每一关有没有解释“为什么这么处理”，而不只是给动作？
- 加粗是否服务提醒，是否会制造 AI 味？
- 工具链接是否准确区分了 demo、代码、数据和项目内部资产？
